# Dotting 场景验证报告

日期：2026-10-08 · 对象：官方 npm 发布包 Dotting 2.1.18

## 1. 结论

**基础像素交互可用，但不建议直接作为当前产品的编辑核心。** 主要原因是大图编辑存在较高同步开销、内部历史无法通过公开属性单独关闭，以及内置导出不符合原尺寸与透明像素保真要求。

建议维持 Next.js + 客户端编辑核心 + Canvas 2D + Worker，自研精简的像素交互与渲染核心，复用 PNG、ZIP 和通用 UI 库。此结论针对 2.1.18、当前需求上限和本次测试，不代表所有版本或小尺寸场景都不适合使用 Dotting。

## 2. 实际验证环境

- 主机：macOS arm64；Node 22.16.0。
- 框架：Next.js 16.4.0、React/React DOM 19.3.0；依赖记录在验证项目锁文件。
- 主要浏览器：本机 Chrome 155.0.8059.39，无头模式。
- 对照浏览器：缓存的 Chromium 111.0.5563.19，无头模式。
- 构建：Next.js 静态生产构建成功，生成首页和默认错误页；本地 HTTP 服务加载导出产物成功。
- 测试：浏览器执行公开 ref 接口；另用真实浏览器鼠标事件测试连续笔画，用键盘 Meta+Z 测试撤销。结果断言均通过，无捕获到的页面运行异常。

GitHub clone 因网络连接失败未取得 checkout，改为下载 npm 发布包，并从其 source map 提取源码。依据是正式发行包，而非未发布的主分支。

## 3. 场景结果

| 场景 | 结果 | 对项目的影响 |
| --- | --- | --- |
| Next.js 客户端挂载与静态构建 | 通过 JS 最小项目验证 | 框架运行时没有直接阻碍，TypeScript 仍需修复包声明入口 |
| 连续绘制 | 从列 1 到列 6 产生六个像素差分，单个 strokeEnd 事件 | 可按一次笔画建立产品历史 |
| 原生鼠标交互及键盘撤销 | 通过 | 不仅公开模拟接口可工作 |
| 修改前后的颜色 | strokeEnd 含 color、previousColor | 具备创建可逆差分的基础 |
| 透明/半透明颜色字符串 | `#11223300`、`#11223380` 原样存取 | 数据模型能够表达完整颜色，并非必然丢失 alpha |
| RGBA 外部数组适配 | 单点写入差分，仅目标像素变化；未编辑透明 RGB 保留 | 可绕开 Canvas 保真问题，但需要产品适配层 |
| 帧 A → B → A 的 setData 切换 | 颜色字符串恢复正确 | 可以显示不同帧，但帧顺序、动画和历史需要产品实现 |
| 内部撤销重做 | 单笔撤销重做正常 | 不覆盖产品帧管理操作 |
| setData 后的历史 | 之前的内部历史被清空 | 不能依靠内部历史实现跨帧项目历史 |
| 关闭 isInteractionApplicable | 不修改数据，但也不发 strokeEnd | 不能简单用此属性关闭内部历史、仍从笔画事件接管修改 |
| 橡皮擦 | 差分颜色是空字符串 | 产品适配时需要归一化为 RGBA(0,0,0,0) |
| 内置 PNG 导出尺寸 | 8×8 图在 gridSquareLength=10 时导出 80×80 | 必须替换导出路径 |
| 内置 PNG 导出透明 RGB | 原透明颜色导出再读取为 (0,0,0,0) | 不满足完全透明下 RGB 保留要求 |
| 发布包类型入口 | package.json 指向 build/src/index.d.ts，该文件不存在；实际为 build/index.d.ts | TS 工程需要别名、补丁或封装声明；JS 构建通过不等于 TS 接入完成 |

RGBA 适配验证覆盖源数组与编辑差分，没有实现独立 PNG 编码器，因此不能把此项解释为完整 PNG 导入导出链路已验收。

## 4. 性能测量

生产静态产物，640×480 显示画布、DPR 1、单图层，源像素统一为非透明颜色。每个尺寸调用三次单像素 colorPixels；另外提交一次有效单点笔画，并确认收到一个 strokeEnd。表中耗时是主线程同步调用时间，不包含下一次画面展示时间，也不是 FPS。

| 源图尺寸 | 单像素 colorPixels 三次范围（Chrome） | 单点笔画提交（Chrome） |
| --- | --- | --- |
| 64×64 | 2.7–3.8 ms | 4.4 ms |
| 256×256 | 35.6–37.7 ms | 49.7 ms |
| 1024×1024 | 871.5–1141.1 ms | 905.0 ms |

Chromium 对照中，256×256 笔画约 75.4 ms，1024×1024 约 1152.5 ms，表现出相同的随源图大小增长趋势。不能据此给所有设备设定精确耗时，但本机大图已有明显阻塞，不符合流畅逐像素编辑的目标。

源码依据：Editor.colorPixels 调用 DataLayer.updateCapturedImageBitmap；该方法遍历所有行列，对像素逐一 fillRect，并重建 OffscreenCanvas 位图。鼠标笔画结束同样触发重建。因此仅修改一个像素也会承担整图遍历开销。问题发生在该组件实现路径，并不证明 Canvas 2D 本身无法胜任。

## 5. 历史接管的代价

可以保留产品 RGBA 数组，监听 strokeEnd 创建项目级命令，拦截组件键盘撤销，并在产品撤销时同步差分或重新 setData。但是内部仍有历史副本和记录开销，公开接口没有单独的关闭历史选项。setData 会清空内部历史并触发整图同步，不适合将每次产品操作都转化为完整替换。

如果 fork 组件以调整历史、图像缓冲、局部刷新与导出，修改已涉及核心结构。本产品首期工具较少，此时精简自研方案更容易维持 RGBA 唯一事实来源。

## 6. 已知验证边界

未完成 Safari/Edge、不同 DPR、上限多帧内存、完整动画、触屏、离开画布与失焦、长时间历史压力测试，也未测量精确峰值内存。运行测试使用本地无头浏览器与少量样本，结果不等于全面生产验收。

源码使用鼠标/触摸事件而非项目计划的 Pointer Events；拖出画布的提交语义需要额外适配或测试。没有为此额外扩大验证范围，因为已测的大图开销足以否定原包直接满足当前完整要求。
